### D-20261013-01 — Минимальное ядро каркаса
- **Статус:** accepted
- **Дата:** 2026-10-13
- **Утверждающий:** Архитектор
- **Контекст:** Три независимых аудита эволюции каркаса (четвёртый раунд) зафиксировали, что полный набор документов избыточен для малых проектов. Модель «библиотека документов» требует явного определения минимального ядра.
- **Решение:** Минимальное ядро любого проекта по KARCAS-DDA — 4 документа:
  - `README.md`
  - `CURRENT_STATE.md`
  - `DECISIONS.md`
  - `INVARIANTS.md`
  
  Остальные документы каркаса подключаются по мере необходимости (модель «библиотека документов»). Расширение минимального ядра — только через accepted-решение.
  
  Перечень активных документов проекта фиксируется в точке входа (`00_ENTRY.md`, если подключён; иначе — в `README.md`). Отдельный раздел в `CURRENT_STATE.md` не создаётся.
  
  Роль Архитектора в форке по умолчанию — владелец репозитория. Определение фиксируется при инициализации проекта.
- **Основание:** Аудиты четвёртого раунда (3 анализа): избыточность полного набора для малых проектов; модель «библиотека документов» как основное направление; необходимость явного минимального ядра.
- **Последствия:** Каркас масштабируется вниз. Малые проекты не платят за полный набор. Перечень активных документов имеет один источник — точку входа.
- **Условие пересмотра:** Если на реальных проектах окажется, что минимальное ядро недостаточно или избыточно.
- **Связанные документы:** README.md, DECISIONS.md (D-20261012-07), 00_ENTRY.md.

### D-20261014-01 — FACT не является типом утверждения; [ФАКТ] = только VERIFIED
- **Статус:** accepted
- **Дата:** 2026-10-14
- **Утверждающий:** Архитектор
- **Контекст:** КОНЦЕПТ12 (MAIA) зафиксировал расхождение: в docs/KNOWLEDGE_STATES.md каркаса три типа (OBSERVATION / RESULT / INTERPRETATION), но FACT там не значится. При этом компактная метка [ФАКТ] склеивала два эпистемических статуса — SUPPORTED и VERIFIED, что противоречит I2 (запрет автоматического перехода SUPPORTED → VERIFIED).
- **Решение:**
  - Типов утверждения — три: OBSERVATION / RESULT / INTERPRETATION. FACT не является типом.
  - Метка [ФАКТ] используется только для VERIFIED.
  - Для SUPPORTED введена отдельная метка [ПОДТВЕРЖДЕНО].
  - Явное указание в §2 и §4 docs/KNOWLEDGE_STATES.md: не путать тип и статус.
- **Основание:** поправки КОНЦЕПТ12 к каркасу (3.1, 3.2); I2.
- **Последствия:** Устраняется семантическая склейка SUPPORTED и VERIFIED. Разметка в проектах становится однозначной.
- **Условие пересмотра:** Если на практике окажется, что разделение [ФАКТ] / [ПОДТВЕРЖДЕНО] избыточно.
- **Связанные документы:** docs/KNOWLEDGE_STATES.md, INVARIANTS.md (I2), meta/handoff-protocol.md §5.

### D-20261014-03 — Дата для роли без терминала; контроль метода; запрет печати личных данных
- **Статус:** accepted
- **Дата:** 2026-10-14
- **Утверждающий:** Архитектор
- **Контекст:** Три поправки КОНЦЕПТ12 к каркасу (3.4, 4.6):

  - Случай вывода `/credentials n8n` с личным email оператора.

- **Условие пересмотра:** Если появятся новые классы срывов передачи.

### D-20261014-07 — Модуль git-hooks: отложен
- **Статус:** accepted
- **Дата:** 2026-10-14
- **Утверждающий:** Архитектор
- **Контекст:** Поправка КОНЦЕПТ12 к каркасу (3.3) предлагала git-hooks как механический предохранитель. При обсуждении выявлено: модуль оправдан, только когда возникает реальный риск (публикация секретов, работа нескольких моделей с репозиторием). Сейчас такого риска нет. При этом был создан meta/git-hooks/README.md без предварительной команды — некорректное действие, зафиксировано ниже.
- **Решение:**
  - Модуль git-hooks остаётся в каркасе как **отложенная тема**. Возврат — при появлении триггера (DeepSeek-администратор коммитит в MAIA; работа нескольких моделей с одним публичным репозиторием).
  - Файл meta/git-hooks/README.md, созданный без команды, оставлен как есть. Отдельного решения по нему нет.
  - Некорректные действия ведущего зафиксированы: (1) создание файла без команды; (2) предложение удалить его без команды; (3) правки без единого компилированного блока.
- **Основание:** поправка КОНЦЕПТ12 к каркасу (3.3); решение Архитектора каркаса (14.10.2026).
- **Последствия:** Тема не потеряна, но и не внедрена преждевременно.
- **Условие пересмотра:** Появление триггера.
- **Связанные документы:** meta/git-hooks/README.md.

### D-20261014-08 — Формат коммита, принцип «исполнитель ≠ проверяющий», патч для точечных правок
- **Статус:** accepted
- **Дата:** 2026-10-14
- **Утверждающий:** Архитектор
- **Контекст:** Три пункта из поправок КОНЦЕПТ12 (3.3, 3.4, N4) и моего P1, оставшиеся после D-20261014-05..07. Формат коммита даёт provenance правок через git blame. Принцип «исполнитель ≠ проверяющий» формализует паттерн внешних аудитов. Патч через git apply сокращает пересылку изменяемых документов целиком.
- **Решение:**
  - `meta/agent-rules.md` §6: добавлен формат сообщения коммита `[<роль> / <модель>] <документ>: что изменено; основание`.
  - §8: добавлен раздел «Точечные правки изменяемых документов через патч» (`git apply --check` перед применением).
  - §10: добавлен подраздел «Исполнитель и проверяющий — разные модели».
  - §11: добавлены два anti-pattern — самовольные действия без команды; правка своего же изменения без внешней проверки.
- **Основание:** поправки КОНЦЕПТ12 (3.3, 3.4, N4); D-20261014-07 (git-hooks отложены, но принцип проверяющего сохраняется процедурно).
- **Последствия:** Правки получают провенанс через git blame. Точечные правки экономят контекст. Проверяющий формализован.
- **Условие пересмотра:** Если формат коммита окажется избыточным для малых проектов; если патч через `git apply` создаёт конфликты на практике.
- **Связанные документы:** meta/agent-rules.md §6, §8, §10, §11.

### D-20261016-01 — Правки каркаса по итогам полевого применения (field-simcord, RUN 0–2)
- **Статус:** accepted
- **Дата:** 2026-10-16
- **Утверждающий:** Архитектор
- **Контекст:** Полевой проект field-simcord применил каркас по образцу ENVOY. За три рана (RUN 0 setup, RUN 0 расширенный, RUN 1, RUN 2) ведущий field-simcord направил четыре отчёта обратной связи. Системные дефекты и пробелы подтвердились неоднократно. Внесены в каркас.
- **Решение:**
  - **`meta/agent-rules.md` §6**: формат коммита допускает `records/run-N/...` как единицу; добавлен подраздел «Работа с длинными файлами и heredoc» (разбивать на блоки, для файлов с фенсед-блоками — редактор).
  - **§8**: исключение для свежесоздаваемых файлов; исключение для крупных raw-выгрузок (raw вне репо + мета-запись с sha256).
  - **§10**: добавлены подразделы «Внешний наблюдатель как штатный узел», «Синтез N внешних выходов».
  - **§11**: добавлены anti-patterns «heredoc с фенсед-блоками или вложенными подстановками shell», «обход закрытого реестра вместо фиксации UNKNOWN».
  - **`docs/METHOD.md`**: §4 — явное отключение ресурсного контура для исследовательских проектов; §7 — пакетирование коммитов, push при отсутствии origin, setup/нулевой/внешне-аудитный ран; §8 — крупные raw-выгрузки, пример ACT-документа, классы источников (веб-страницы, документы, реестры, технические источники, внешние наблюдатели), восстановление сырья; §11 — копия нормативных документов каркаса, рекомендация о границах и о разделении «факт публикации ≠ истинность содержания».
- **Основание:** четыре отчёта ведущего field-simcord (RUN 0, RUN 0 р., RUN 1, RUN 2); подтверждение системных дефектов неоднократным применением.
- **Последствия:**
  - Полевой профиль каркаса становится применим без правок в поле.
  - Устраняется ad hoc-практика: процедура внешнего наблюдателя, синтез N выходов, схема работы с крупными raw, шаблоны ACT и setup-рана — теперь в каркасе.
  - Трение §8 agent-rules снято исключениями, не нарушающими I3.
- **Условие пересмотра:** Если на других полевых проектах новые подразделы окажутся избыточными или потребуют доработки.
- **Связанные документы:** meta/agent-rules.md §6, §8, §10, §11; docs/METHOD.md §4, §7, §8, §11.
