# docs/METHOD.md
Метод исследования и полевой работы.
Заполняется, если проект включает сбор данных, эксперименты, полевую разведку или работу с внешней средой.
Для проектов без исследовательской части может оставаться заготовкой.

## 2. Базовый принцип

**Сначала поле, потом модель.**

Реальность не втискивается в заранее заданную гипотезу.
Наблюдение, действие, результат и интерпретация остаются различимыми.

## 4. Два контура

Контуры могут взаимодействовать, но не должны смешиваться.

### Исследовательский контур

    Field → observation → data → hypothesis → test → knowledge

### Ресурсный контур

    Field → need → opportunity → action → result → potential resource

**Запрещено:**

- считать исследовательский результат автоматически продуктом;
- считать коммерческую возможность автоматически научным выводом.

### Отключение ресурсного контура

Если проект чисто исследовательский, ресурсный контур отключается явно, записью в DECISIONS. Отсутствие записи означает, что контур активен (хотя бы потенциально).

## 5. Состояния знания

Базовая модель — см. `docs/KNOWLEDGE_STATES.md`.

Кратко, для полевой работы:

- `FACT` / `[ФАКТ]` — VERIFIED, подтверждено источником или документированным наблюдением.
- `[ПОДТВЕРЖДЕНО]` — SUPPORTED, проверка неполная.
- `HYPOTHESIS` / `[ГИПОТЕЗА]` — проверяемое объяснение.
- `UNKNOWN` / `[НЕИЗВЕСТНО]` — неизвестно.

Запрещены автоматические переходы:

    Observation → Fact
    Hypothesis → Fact
    Unknown → Assumption

Переходы фиксируются в `meta/transitions.md`.

## 6. Минимальная полевая запись

См. `records/README.md`. Обязательные поля:

    FIELD / OBSERVATION / SOURCE / ACTION / RESULT /
    INTERPRETATION / HYPOTHESIS / UNKNOWN / NEXT STEP

Расширения при необходимости: `TIMESTAMP`, `PROVENANCE`, `ACTOR`, `CONTEXT`, `CONFIDENCE`.

## 7. Run Structure (структура прогона)

Каждый завершённый прогон обязательно производит:

1. Запись прогона (run record).
2. Сохранённые сырые внешние выходы (или явный маркер `UNKNOWN` / `archived-external`).
3. Отдельный синтез ведущего (Lead synthesis).
4. Явное решение, если оно было принято.
5. Явное следующее наблюдение.
6. Git commit.
7. Git push в origin/main.

**Правило:** следующий прогон не начинается, пока предыдущий завершённый прогон не задокументирован.

### Пакетирование коммитов

Допускается пакетирование коммитов в конце прогона, если работа велась единой логической единицей. Каждый коммит должен иметь осмысленное сообщение по формату §6 agent-rules. Дробление на много мелких коммитов ради формального соблюдения правила не требуется.

### Push при отсутствии origin

Если удалённый репозиторий не подключён (setup-ран, локальный проект):

- в run record явно указывается «push отложен, причина: origin не настроен»;
- завершение прогона не блокируется;
- при подключении origin — первый push включает все накопленные коммиты;
- в CURRENT_STATE фиксируется статус «локальный, зеркало не подключено».

### Setup / нулевой / внешне-аудитный ран

Для рана, который не является полевым циклом (setup, вводная проверка, внешний аудит репозитория):

- run record формируется как LEAD SYNTHESIS: что сделано, что обнаружено, что решено;
- полевые OBS/ACT не создаются (нечего наблюдать или действовать);
- решения фиксируются в DECISIONS как обычно;
- git commit и (при наличии origin) git push — как в §7.

Такой ран не блокирует старт первого содержательного рана. Но и не считается полем — это подготовительный контур.

## 8. Провенанс (слои)

Слои должны оставаться различимыми:

- `raw-external` — захвачено в момент прогона.
- `archived-external` — повторно выданное источником из persistent-чата на указанную дату.
- `RUN RECORD`
- `LEAD SYNTHESIS`
- `DECISION`
- `NEXT OBSERVATION`

Сырые внешние выходы не редактируются молча. Ошибки, загрязнения, противоречия и отклонения сохраняются и классифицируются в синтезе.

### Крупные raw-выгрузки

Если внешний выход превышает ~20 КБ:

- raw сохраняется вне git-репозитория (например, `~/raw-external/`);
- в `records/` хранится мета-запись: путь, размер, sha256, дата, наблюдатель, источник;
- запись в `records/` ссылается на raw по sha256 и обеспечивает целостность;
- это не нарушает I3 — первичные данные сохранены и верифицируемы.

### Пример ACT-документа

ACT — действие, выполненное в поле. Формат:

    ACT-NNN — <краткое название>
    ПРОЦЕДУРА: <что было сделано, каким инструментом>
    РЕЗУЛЬТАТ: <что получено>
    ОГРАНИЧЕНИЯ: <что не удалось, где закрыт доступ>
    СВЯЗАННЫЕ OBS: <номера наблюдений>
    PROVENANCE: <ссылка на raw или мета-запись>

ACT отличается от OBS наличием процедуры (у OBS — только фиксация).

### Классы источников

Полевые источники делятся на классы:

- **веб-страницы** — сайты, публикации, СМИ;
- **документы** — PDF, сканы, официальные бумаги;
- **реестры** — YouControl, OpenCorporates, firmas.lv, судебные реестры (см. ниже);
- **технические источники** — WHOIS/RDAP, DNS, TLS/CT-логи, GitHub API;
- **внешние наблюдатели** — LLM-модели, привлекаемые по заданию.

Каждый класс имеет свою процедуру работы. Технические источники работают пассивно (запрос — ответ), не требуют обхода. Реестры могут быть закрыты (SPA, API-ключ, Cloudflare) — в этом случае фиксируется UNKNOWN, обход запрещён.

### Восстановление утраченного сырья

Если сырьё не было захвачено в момент прогона:

- источник может быть попрошен выдать свой прежний ответ повторно из persistent-чата;
- повторно выданный ответ сохраняется как `archived-external`, не как `raw-moment`;
- архивная запись фиксирует: узел, чат, номер сообщения, дату повторной выдачи;
- если дословный ответ не сохранён — прогон фиксирует `UNKNOWN`;
- ведущий не реконструирует утраченный выход из памяти или по резюме.

Реконструкция никогда не используется вместо `raw` или `archived` выхода.

## 9. Git Rule

После каждого завершённого прогона:

1. Сохранить сырые выходы (в репо или вне репо по §8).
2. Заполнить run record.
3. Заполнить Lead synthesis.
4. Зафиксировать решение и следующее наблюдение.
5. Commit.
6. Push в `origin/main` (если origin есть — см. §7 «Push при отсутствии origin»).
7. Проверить: локальный HEAD, удалённый HEAD, чистое рабочее дерево.

Git — постоянная внешняя память проекта.

## 10. Quiet presence

Публичность, если она появляется, — следствие полевой работы, а не её предпосылка.

Операционный приоритет:

    observe before declare
    understand before scale
    test before conclude

## 11. Связь с другими проектами

Проект независим. Может:

- использовать знания и методы других проектов;
- передавать проверенные результаты;
- порождать новые исследовательские вопросы;
- порождать ресурсы для дальнейшей работы.

Провенанс остаётся раздельным:

    LAB fact
    != Corpus representation
    != <this project> observation
    != <this project> interpretation
    != <this project> result

Общие источники не означают общую идентичность проектов.

### Копия нормативных документов каркаса

При развёртывании полевого проекта из каркаса допускается:

- скопировать нормативные документы (INVARIANTS, agent-rules, handoff-protocol и т. п.) в проект без переписывания;
- зафиксировать источник копии записью в PROVENANCE (P-запись с указанием каркаса, даты, sha коммита);
- при обновлении каркаса — решение об обновлении копии принимается явно, не автоматически.

### Рекомендация для полевых проектов

- До начала работы явно зафиксировать в VISION границы: что исследуется, что НЕ исследуется. Это снимает класс этических и правовых рисков до старта.
- При работе с публичными заявлениями, медиа, реестрами — разделять «факт публикации» и «истинность содержания». Публикация утверждения — наблюдаемый факт; истинность утверждения требует отдельной проверки.

## 12. Память экспедиции

Сохраняется не только вывод, но и путь к нему:

    WHAT WAS SEEN
    ↓
    WHAT WAS THOUGHT
    ↓
    WHAT WAS DONE
    ↓
    WHAT HAPPENED
    ↓
    WHAT CHANGED
    ↓
    WHAT REMAINS UNKNOWN

Это позволяет учиться на полевом опыте, а не только на итоговых выводах.
