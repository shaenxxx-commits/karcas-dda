# meta/agent-rules.md
Правила работы LLM-агента в проекте.
Документ читается после 00_ENTRY.md, применяется наравне с INVARIANTS.md.
Если правило здесь противоречит INVARIANTS.md — приоритет за INVARIANTS.md.

## 1. Нумерация ответов

- Формат: MS N — отдельной первой строкой ответа, ничем не предваряется.
- Один номер на один ответ. Не нумеровать шаги, задачи или блоки кода внутри одного ответа отдельными MS.
- Внутри блоков кода номер MS не ставится.
- Нумерация сквозная в рамках одного чата, начинается с 1, не сбрасывается между задачами.

## 2. Формат ответов

- Коротко, без воды. Не раздувать.
- Один шаг за раз. Не забегать вперёд.
- Одна команда → вывод → следующая. Не стекать команды даже если они логически связаны.
- Промпты и команды — copy-paste одним блоком, без вложенных пояснений.
- Не повторять известное.
- Язык ответа — язык запроса. Короткий запрос — короткий ответ, подробный запрос — развёрнутый.
- Каждое сообщение потребляет контекст чата. В длинных сессиях — экономить.

## 3. Режимы взаимодействия

- «Обсудим» / «пока обсуждаем» / «набросай идею» — режим обсуждения. Не выдавать промпты, черновики, команды, готовые блоки. Только анализ, варианты, позиция.
- Действия (промпты, команды, блоки, правки) — только по явной команде.
- Обсуждение идеи не является командой действовать. Собирать блок только когда прямо попросили.
- «Один шаг за раз» — не давать следующий шаг до получения вывода предыдущего.
- Самовольные действия (создание, удаление, изменение файлов без команды) — нарушение протокола. Если действие кажется нужным — предложить, ждать решения.

## 4. Варианты и рекомендации

- Не давать варианты без рекомендации.
- Помечать выбор: [ПРЕДПОЧТИТЕЛЬНО].

## 5. Работа с фактами

- Прямо и честно, включая ограничения.
- Не додумывать. Спрашивать или помечать [НЕИЗВЕСТНО].
- Явная атрибуция внешних наблюдателей.
- Ошибка в предыдущем ответе — признать прямо, откатить, не защищать формулировку.
- Не задавать вопросов ради вопроса. Если ответ очевиден из контекста или зафиксирован в документе — не спрашивать.

## 6. Работа с терминалом

- Команды — готовы к вставке одним блоком.
- Результат команды — в чат.
- Не предполагать, что оператор помнит расположение файлов. Указывать явно.
- Перед командой уточнять pwd, если это значимо. Ошибки «файл не найден» — часто из-за неверного каталога.
- После git push — дождаться git log -1 --oneline и git status --short. Не считать успешным без подтверждения вывода.

### Формат сообщения коммита

Шаблон: [роль / модель] документ: что изменено; основание

- Роль — одна из: Архитектор, КОНЦЕПТ, УЧ, РЧ, ведущий, агент.
- Модель — свободное поле: Claude, DeepSeek, Kimi, Luna, Namazu, человек.
- Документ — целевой файл или группа файлов. Допускается единица рана: records/run-N/...
- Что изменено — краткое описание.
- Основание — ссылка на запись в DECISIONS, если применимо.

Пример:

    [ведущий / DeepSeek] INVARIANTS.md: уточнён I3, добавлен механизм разового исключения; D-20261014-05

Формат даёт provenance правок через git blame — кто и на каком основании внёс изменение, без отдельного документа.

### Работа с длинными файлами и heredoc

Heredoc ненадёжен для содержимого, которое само содержит:
- фенсед-блоки markdown (тройные backtick);
- вложенные heredoc;
- строки с подстановками shell (обратные кавычки, $).

Признаки: команда «виснет», ожидая EOF; содержимое обрезается; в файл попадает мусор.

Правила:
- Разбивать содержимое на несколько коротких блоков (cat > для первого, cat >> для последующих).
- Для файлов с фенсед-блоками — писать через nano/редактор, а не через heredoc.
- Альтернатива: записать файл через python3 -c с многострочной строкой, но это тоже требует осторожности.
- После записи — всегда проверять wc -l и tail (5 строк) до продолжения.

## 7. Даты

- Перед записью в файл, где требуется дата, — получить её через команду date в терминале. Вывод — единственный источник даты.
- Не выводить дату из контекста, предыдущих ответов, предположений о времени сессии.
- Если дата ещё не получена — не писать документ, где она нужна, или ставить явную пометку [ДАТА НЕ ЗАФИКСИРОВАНА].
- Для роли без терминала (например, чат в Claude Projects, работающий только с текстом): допустимый источник даты — дата сервера из терминального вывода, полученного оператором, или из отчёта оператора. Не из памяти агента и не из содержания документов.

## 8. Формат правки документов

- Формат правки — весь документ целиком, одним блоком, готовым для копипаста.
- Не диф, не фрагмент «вставить после раздела X».
- Правки документов — только по явной санкции на каждую правку. Согласие с чем-то не является санкцией на редактирование.
- Правки могут накапливаться в явном списке до отдельной команды на комплексную редакцию.

**Исключение для append-only журналов.** Для документов, которые по своему режиму являются append-only (DECISIONS.md, PROVENANCE.md, meta/transitions.md, meta/open-questions.md, records/), полная выдача документа расточительна: существующие записи не меняются. Допускается выдача фрагментом — «добавить в конец» с явной пометкой места вставки.

**Исключение для свежесоздаваемых файлов.** Когда файл создаётся впервые, содержимое уже есть в контексте (только что обсуждалось). Повторная выдача целого документа дублирует контекст. Допускается:
- запись через команду с кратким подтверждением (wc -l + tail);
- для коротких файлов (до ~50 строк) — целиком, без изменений;
- для длинных — разбивать на блоки.

**Исключение для крупных raw-выгрузок.** Если внешний выход превышает ~20 КБ:
- сохранять raw вне git-репозитория (например, ~/raw-external/);
- в records/ хранить мета-запись: путь, размер, sha256, дата, наблюдатель;
- это не нарушает I3 (первичные данные сохранены), но экономит контекст и место в репо.

Требование «документ целиком» остаётся обязательным для изменяемых нормативных документов: INVARIANTS.md, CURRENT_STATE.md, README.md, 00_ENTRY.md, meta/agent-rules.md, meta/handoff-protocol.md, meta/handoff-current.md, docs/*.md.

### Точечные правки изменяемых документов через патч

Для изменяемых документов при работе с исполнителем, имеющим доступ к репозиторию, допускается альтернатива: правка в виде патча.

- Патч формируется как diff-фрагмент с явным контекстом.
- Перед применением: git apply --check patch-file — проверка, что патч применится без конфликтов.
- Только после успешной проверки: git apply patch-file.
- После применения: git diff — подтверждение результата; коммит в формате §6.

Патч не заменяет полную выдачу для крупных правок. Для мелких (одна строка, один раздел) — экономит контекст. Для правок нормативных документов (INVARIANTS, CLAUDE) патч применять нельзя — только целый документ или ветка с ревью.

## 9. Зачистка мусора

- Временные, тестовые файлы, черновые запросы, промежуточные экспорты — удалить или явно пометить на удаление до отчёта, не после.
- Если что-то оставлено намеренно — указать причину в отчёте.

## 10. Работа с источниками и внешними узлами

- Внешние наблюдатели используются постоянно (Luna, Grok, Kimi, Namazu и т. д.). Это не сигнал недоверия, а усиление.
- Атрибуция сохраняется: [ВНЕШНИЙ — Luna], [ВНЕШНИЙ — Grok].
- Компиляция выводов внешних — извлекать полезное, не усреднять. Подлинные конфликты показывать как есть, не сглаживать.
- Если дословный текст наблюдателя в текущем чате не прислан — не восстанавливать его по памяти.
- Контроль метода: при замере «не найдено» в ту же выборку включать заведомо найденные записи (минимум 5). Иначе ноль неотличим от ошибки метода.
- Не печатать вывод команд, содержащий личные данные оператора (email, токены, пути с идентификаторами), даже если оператор его прислал.

### Внешний наблюдатель как штатный узел

Внешний наблюдатель — модель или сервис, привлекаемый для независимой проверки. Процедура привлечения:

1. Сформулировать задание: что проверить, в каком объёме, в каком формате ответа.
2. Задание адресуется наблюдателю явно, с пометкой адресата.
3. Ответ сохраняется как raw (см. §8 — исключение для крупных raw).
4. В мета-записи фиксируется: имя наблюдателя, версия модели (если называет), дата, sha256 raw, путь.
5. В рабочем документе ответ наблюдателя цитируется с атрибуцией [ВНЕШНИЙ — <имя>].
6. Если дословный ответ не сохранён — фиксируется UNKNOWN, реконструкция по памяти недопустима.

### Синтез N внешних выходов

Когда привлекается несколько наблюдателей по одному заданию:

- Каждый ответ сохраняется отдельно, с собственной атрибуцией.
- Совпадения фиксируются как SUPPORTED (если подтверждены независимо).
- Расхождения фиксируются как есть — не сглаживаются, не усредняются.
- Явные противоречия выносятся в DECISIONS или в open-questions, если решение отложено.
- Синтез оформляется отдельным документом (LEAD SYNTHESIS) со ссылками на raw-выборки.
- Мнение большинства не заменяет проверку по первоисточникам.

### Исполнитель и проверяющий — разные модели

Принцип: агент, который вносит изменение, не проверяет его сам.

- Ревью правок и коммитов выполняет другая модель или другой чат.
- Ревью проводится по пакету коммитов (git log -p по диапазону), не по каждому отдельно.
- Нормативные правки (INVARIANTS, CLAUDE, 00_ENTRY, README) — ревью до коммита, в ветке.
- Объём ревью ограничен — иначе расход контекста проверяющего смещает экономию исполнителя.
- Если проверяющего нет — статус правки остаётся proposed, не accepted.

## 11. Anti-patterns

Нарушениями протокола считаются:

- выдумывание отсутствующего состояния проекта;
- утверждение, что файл прочитан, когда он не читался;
- утверждение, что команда выполнена, когда не выполнялась;
- утверждение, что правка произошла, когда её не было;
- обращение со старым handoff как с текущим состоянием;
- выдача собственного анализа за вывод внешнего наблюдателя;
- приписывание наблюдателю придуманного высказывания;
- молчаливое разрешение конфликта источников;
- молчаливое изменение смысла решения оператора;
- старт зависимой операции при непроверенном состоянии;
- «делай как раньше» без явно определённой операции;
- реконструкция утраченного сырья по памяти;
- самовольные действия без команды (создание, удаление, изменение);
- правка своего же изменения тем же агентом без внешней проверки;
- heredoc с фенсед-блоками или вложенными подстановками shell;
- обход закрытого реестра (SPA, API-ключ, Cloudflare) вместо фиксации UNKNOWN.

До канонизации протокола нарушения трактуются как отказ протокола, а не как стилистический дефект.

## 12. Передача контекста

- Передача между сессиями и агентами — через meta/handoff-current.md по формату meta/handoff-protocol.md.
- Новый агент не принимает handoff на веру. Обязательные шаги старта — см. meta/handoff-protocol.md.
